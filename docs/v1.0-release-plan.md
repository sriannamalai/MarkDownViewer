# MarkDownViewer v1.0 Release Plan

## Summary
This plan defines the work required to release the MarkDownViewer Library and MDViewer.Desktop as v1.0.0. It also defines the progressive MDViewer.Mobile milestones that Sri added during the release interview. The Library remains the dependency spine. Library features and compatibility work land first. The Library then tags v1.0.0 and flutter-v1.0.0. Desktop and Mobile re-pin that release before their own release work finishes.

This is a feature train followed by a stability release. It is not only an API freeze. Sri requires CLI PDF output and complete HTML-to-native semantic feature mapping before the Library reaches v1.0.0. Sri also requires Desktop window drag and resize on macOS, Windows, and Linux. Mobile does not use a v1.0 label because its published tags have already reached v2.2.

## Release outcomes
- The Library ships `v1.0.0`.
- The Flutter plugin ships `flutter-v1.0.0`.
- The CLI creates HTML and real PDF files.
- The HTML renderer and native render tree have a complete, tested semantic mapping.
- Each public Library surface has a written compatibility class and an automated compatibility check.
- Desktop consumes Library v1.0.0 and ships `v1.0.0` independently.
- Desktop keeps its HTML/webview architecture.
- Desktop supports window drag and edge/corner resize on macOS, Windows, and Linux.
- Mobile consumes `flutter-v1.0.0`.
- Mobile uses progressive v2.x releases and culminates in `v3.0.0` for the multi-vault, wiki navigation, PDF, and store-distribution train.
- Every release document states the actual version, architecture, pin, and limitation. No release ships with known false project-memory claims.

## Scope decisions
Sri made these decisions during the release interview:
- Library v1.0 is a feature-and-freeze release.
- CLI PDF is required before Library v1.0.
- The HTML and native render paths must map the complete document feature set before Library v1.0.
- The default freeze matrix in this plan is approved.
- Library v1.0 ships before Desktop v1.0. The releases are not required to ship on the same day.
- Desktop uses the recommended middle product bar.
- Desktop also requires window drag and resize on macOS, Windows, and Linux.
- Desktop does not adopt the native render tree. This is a permanent architectural decision.
- Library incremental rendering is not required.
- Mobile multi-vault, PDF, wiki navigation, and production signing are required.
- Mobile is now a milestone target, but it does not use the v1.0 release name.
- Mobile versions advance progressively from the existing `v2.2` tag.

## Assumptions pending confirmation
The following assumptions allow work to proceed without another planning delay:
- **CLI PDF backend:** `mdview` invokes a Chromium-family executable on the host. The CLI does not embed a browser or a pure-Go PDF engine. A missing executable produces a clear error.
- **Native feature waivers:** Non-heading raw-HTML fragment targets and `mailto:`/`tel:` taps remain host-level waivers for this release train. Heading fragments, wiki links, HTTP(S) links, relative Markdown links, and exact footnote targets remain required.
- **Mobile PDF and distribution:** Mobile creates a real PDF file that the user can save or share. A print dialog alone does not pass. Production signing means a signed Android App Bundle reaches a Play internal track and a signed iOS archive reaches TestFlight.
- **Additional public surfaces:** The public Go facade, CLI contract, WASM exports, and HTML semantic/safety contract use the frozen-append-only class. They were not named separately in the interview matrix, but a public Library v1.0 must define their compatibility.
- **Mobile package identity:** Android and iOS use `dev.sriannamalai.mdviewer` unless an existing store record requires a different permanent identifier.

If Sri rejects an assumption, revise only the affected milestones and compatibility text. Do not reopen the decisions that Sri already made.

## Release definitions
- **Frozen-append-only** means an existing public name, numeric value, field, signature, behavior, or documented meaning cannot be removed, renamed, renumbered, narrowed, or repurposed during v1.x. A release can add optional fields, new enum values, new symbols, new methods with defaults, or new assets when old consumers continue to work.
- **Frozen-no-additions** means the v1 shape is closed. A new field or key requires a new explicitly versioned schema. Existing v1 readers and writers keep the exact v1 shape.
- **Experimental** means a surface is clearly labeled before v1.0.0 and can change in a v1 minor release. No surface listed as frozen can later be relabeled experimental.
- **Semantic parity** means both renderers represent the same parsed document meaning and policy decision. It does not mean both renderers produce the same layout or pixels.
- **Release candidate** means a commit that has passed every repository-local gate and every required cross-repository regression. Only release notes, release-blocking fixes, and version metadata can change after the candidate is selected.

## Library v1 freeze matrix
The compatibility document created by Milestone L4 must state every item below.

### Public Go facade
- Class: **frozen-append-only**.
- Frozen content: exported packages, functions, types, constants, option functions, error behavior, and documented ownership/concurrency contracts.
- Permitted after v1.0: new exported APIs and optional behavior selected by new options.
- Not permitted during v1.x: removing or changing an existing signature, changing a default in a way that breaks documented output or safety, or moving a public symbol without a compatible forwarding path.

### Document `Kind` values 0 through 31
- Class: **frozen-append-only**.
- Frozen content: every numeric value, lower-camel wire name, node meaning, and current required field.
- Permitted after v1.0: append a new numeric value and wire name. Existing values cannot move.
- Not permitted during v1.x: renumbering, reusing, renaming, or changing the meaning of a current kind.

### Document JSON schema version 1
- Class: **frozen-append-only**.
- Frozen content: the version-1 envelope, kind names, current required fields, field types, and current field meanings.
- Permitted after v1.0: optional fields and newly appended kinds. Older Go readers continue to ignore unknown optional fields. They fail loudly on an unknown kind and require an upgrade, as the current codec documents.
- Not permitted during v1.x: removing a field, changing a field type or meaning, making an optional field required, or changing the envelope. An incompatible change requires document JSON version 2.

### Options JSON schema version 1
- Class: **frozen-no-additions**.
- Frozen content: the exact top-level and nested parser key sets in `internal/boundary/options.go`, exact casing, defaults, types, strict unknown-key rejection, and version behavior.
- Permitted after v1.0: bug fixes that preserve those inputs and results.
- Not permitted: adding a key to version 1 or changing an existing key. Any new option requires an options JSON version 2 decoder and an explicit selection path. A version-1 payload must keep its current meaning.

### C ABI
- Class: **frozen-append-only**.
- Frozen content: all 13 `mdv_*` symbols, signatures, return codes, allocator pairing, callback ownership, UTF-8 buffer contract, panic-to-error behavior, and `ResolveKind` values 0 through 2.
- Permitted after v1.0: a new symbol with a distinct name or an appended `ResolveKind` value when old callbacks can decline it.
- Not permitted during v1.x: removing a symbol, changing an argument or return type, changing ownership, renumbering a `ResolveKind`, or adding a required argument to an existing function.

### WASM and npm wrapper
- Class: **frozen-append-only**.
- Frozen content: current exported function names, argument and result shapes, resolver callback behavior, and current TypeScript declarations.
- Permitted after v1.0: new exports and optional result fields that preserve old callers.
- Not permitted during v1.x: removing or renaming an export, changing a current call shape, or weakening resolver and sanitization behavior.

### Native render-tree schema version 1
- Class: **frozen-append-only**.
- Frozen content: the envelope, current block and inline kinds, required fields, field types, ID rules, source spans, resolution results, footnote pairing, and unknown-kind fallback contract.
- Permitted after v1.0: optional fields and new kinds. Hosts must keep an unknown-kind fallback.
- Not permitted during v1.x: removing or repurposing a kind or field, changing a type, or changing a required field. An incompatible change requires render-tree schema version 2.

### Flutter plugin widget and adapter API
- Class: **frozen-append-only**.
- Frozen content: current public Dart names, constructors, required parameters, callback signatures, typed tree models, default widget behavior, and adapter key/index contracts after the pre-freeze footnote split.
- Permitted after v1.0: new optional named parameters, new types, new callbacks, and new adapter queries with compatible defaults.
- Not permitted during v1.x: removing a name, adding a required parameter, changing a callback signature, or changing existing default behavior without an opt-in.

### Asset registry
- Class: **frozen-append-only**.
- Frozen content: every current case-sensitive asset name, MIME/content category, offline availability, JSON schema version, and lookup/error contract.
- Permitted after v1.0: new asset names and compatible updates to implementation bytes. Mermaid, KaTeX, CSS, and palette content can receive compatible bug and security updates.
- Not permitted during v1.x: removing or renaming an asset, changing a JSON field incompatibly, returning network stubs, or changing the meaning of a current name.

### HTML output
- Class: **frozen-append-only semantic contract**.
- Frozen content: sanitize-by-default behavior, safe URL policy, offline full-page output, fragment behavior, documented CSS variables, source-map attributes, resolver trust boundary, and conditional Mermaid/KaTeX support.
- Permitted after v1.0: byte-level markup and CSS improvements that preserve documented hooks and behavior.
- Not frozen: byte-for-byte HTML, private class names, whitespace, and browser-specific layout.
- Not permitted during v1.x: weakening safety defaults, adding network dependencies, or removing a documented host hook without a compatible replacement.

### CLI
- Class: **frozen-append-only**.
- Frozen content: current flags and defaults plus the PDF interface defined in Milestone L1, stdin behavior, stdout/file behavior, exit status, and error prefix.
- Permitted after v1.0: new optional flags and new output formats.
- Not permitted during v1.x: removing or repurposing a flag, silently changing a default, or changing an error case into partial success.

### Explicitly experimental or unfrozen
- Internal packages, implementation types, generated temporary files, and private DOM classes are not public contracts.
- Exact HTML bytes are not stable.
- Exact PDF bytes, page breaks, and font metrics are not stable across supported Chromium versions.
- Incremental rendering does not exist in v1 and has no compatibility promise.
- Desktop native-tree rendering is not an experiment. It is deliberately out of scope.
- Host layout engines for live Mermaid and KaTeX remain host implementations. The asset lookup, diagram/math source nodes, palette data, and plugin hooks are frozen as described above.

## Critical path and parallel work
The critical path is:

1. Milestone P0 corrects release memory and creates the tracking baseline.
2. Milestones L1, L2, and L3 run in parallel.
3. Milestone L4 starts after L1, L2, and L3 finish.
4. Milestone L5 validates the Library release candidate.
5. Milestone L6 tags `v1.0.0` and `flutter-v1.0.0`.
6. Milestones D1 and M1 re-pin the released artifacts.
7. Desktop Milestones D2 and D3 run in parallel after D1.
8. Desktop Milestones D4 and D5 finish Desktop v1.0.

Mobile Milestones M2, M3, and M4 can run in parallel after M1 if separate owners work in isolated branches. M5 depends on credentials from Sri and can prepare CI in parallel, but it cannot pass until those credentials and store records exist. M6 integrates all Mobile work.

The Mobile feature train does not block the Library or Desktop v1 tags after the Library-owned plugin work in L3 and the consumer re-pin in M1 pass. This preserves Sri's decision that Library and Desktop ship independently.

## Planning schedule
This schedule assumes one primary maintainer and reviewers who respond within one working day.

- **Week 1:** P0 starts. L1, L2, and L3 start in parallel.
- **Weeks 2–3:** L1–L3 finish. L4 creates the freeze contract and guards.
- **Week 4:** L5 release candidate and L6 Library tags.
- **Weeks 5–6:** D1, D2, and D3. M1 runs in parallel.
- **Week 7:** D4 release candidate and D5 Desktop v1.0.0.
- **Weeks 5–10:** M2–M4 progressive Mobile releases.
- **Week 10 or later:** M5 store credential gate and M6 Mobile v3.0.0.

The Library/Desktop critical path is approximately seven weeks for one maintainer. Two independent implementation owners can shorten it to approximately four or five weeks because L1–L3 and D2–D3 are parallel. The Mobile date remains conditional on store credentials and review times.

### L1 — Add real PDF output to `mdview`
**Repository:** MarkDownViewer

**Depends on:** P0 can remain in review.

**Can run in parallel with:** L2 and L3.

**Interface:**
- Add `-format html|pdf`. The default remains `html`.
- Require `-o <file.pdf>` for `-format pdf`. Do not write binary PDF bytes to an interactive terminal.
- Reject `-fragment` with `-format pdf`.
- Apply `-theme`, `-unsafe`, `-no-mermaid`, `-no-math`, `-no-highlight`, and `-width` before PDF conversion.
- Add `-chromium <path>` for deterministic CI and nonstandard installations.
- Without `-chromium`, search supported Chromium-family executable names on `PATH`.
- Return a non-zero exit with an actionable message when no executable is found.
- Render a full, self-contained temporary HTML file. Invoke Chromium headlessly with network disabled and enough virtual-time budget for Mermaid and KaTeX to finish. Remove the temporary file on success and failure.
- Write to a temporary PDF path and atomically move it to `-o` only after Chromium exits successfully and the output begins with the PDF signature.
- Keep PDF CLI-only. Do not add a PDF symbol to the C ABI, WASM, Go facade, or Flutter plugin.

**Required tests:**
- Unit tests use a fake Chromium executable to verify arguments, exit propagation, temporary-file cleanup, output validation, and spaces in paths.
- CLI tests cover stdin input, file input, all incompatible flags, missing browser, browser failure, and no partial destination on failure.
- An integration test uses the CI-installed Chromium binary and a fixture containing headings, tables, syntax highlighting, images, KaTeX, Mermaid, footnotes, and more than one page.
- The integration test runs with outbound network blocked.

**Exit criteria:**
- `go test ./cmd/mdview/...` passes.
- `go test -race ./...` passes.
- `go vet ./...` passes.
- `gofmt -l .` prints nothing.
- `mdview -format pdf -chromium "$CHROMIUM" -o /tmp/mdview.pdf testdata/release-showcase.md` exits 0.
- `file /tmp/mdview.pdf` reports a PDF document.
- Required visual proof is attached to the milestone: a video opens the generated PDF, pages through it, and shows rendered Mermaid, KaTeX, a table, highlighted code, a footnote, and page 2 content. A screenshot is insufficient because multi-page output and delayed diagram rendering must be demonstrated.

## Explicit post-1.0 deferrals

### Library
- Incremental rendering is deferred because no measured host workload requires it.
- Stronger global resource-exhaustion bounds are deferred because the current context APIs bound caller latency but a correct parser-level CPU bound needs separate design.
- A PDF C ABI, PDF WASM API, PDF Go facade, and PDF Flutter plugin are deferred because the requested PDF use case is the CLI. Adding browser dependency behavior to embedded surfaces would enlarge and complicate every host.
- A pure-Go PDF renderer is deferred because it would duplicate HTML layout and create a permanent fidelity gap.
- Non-heading raw-HTML fragment metadata is deferred under the pending waiver. Reopen it only if Sri rejects the waiver.

### Desktop
- Native render-tree adoption is permanently out. Desktop remains the HTML/webview flagship.
- Native operating-system chrome is deferred. Unified custom chrome remains the only mode.
- Print-theme, page-number, and table-of-contents export controls are deferred because no approved Library option supplies them.
- Broad pixel-perfect rework of every screen is deferred. Release proof covers the v1 critical flows and renderer showcase.

### Mobile
- Incremental rendering is not required.
- Cross-vault aggregate search is deferred. Multi-vault v2.4 searches the active vault.
- Non-heading raw-HTML fragments and `mailto:`/`tel:` taps are deferred under the pending waiver.
- Editing, file management, cloud sync, and collaboration are out because the product remains a read-only viewer.

## Deliberate trade-offs

### Chromium CLI PDF instead of an embedded PDF engine
- Chosen: an external Chromium-family executable.
- Advantage: matches HTML, Mermaid, KaTeX, CSS, and fonts without adding a second layout engine.
- Advantage: does not enlarge `libmdviewer`, WASM, or Mobile binaries.
- Cost: CLI hosts must install Chromium.
- Rejected: in-process browser control libraries because they add a large browser-management dependency.
- Rejected: pure-Go PDF because it duplicates layout and cannot reach renderer fidelity within this release.

### Semantic parity instead of pixel parity
- Chosen: one parser and policy layer with two renderer-specific presentation paths.
- Advantage: every document feature is representable without forcing a web layout into native widgets.
- Advantage: current differential tests and shared `derive`/`resolve` packages remain the source of truth.
- Cost: hosts still implement layout and live math/diagram engines.
- Rejected: copying HTML page options into the tree because CSS, fragments, and source-map attributes are not native semantic concepts.

### Options JSON v1 is closed
- Chosen: frozen-no-additions.
- Advantage: strict readers keep an exact contract and typos keep failing.
- Cost: the next cross-boundary option requires explicit schema version 2 work.
- Rejected: adding optional v1 keys because old strict readers reject them and the result would not be append-compatible.

### Independent Library and Desktop releases
- Chosen: Library tags first; Desktop follows after re-pin.
- Advantage: Library consumers can adopt v1 without waiting for Desktop UI work.
- Advantage: Desktop can fix release-candidate issues without moving the Library tag.
- Cost: release communication spans two dates.
- Rejected: same-day hard coupling because no technical dependency requires it after the re-pin passes.

### Progressive Mobile versions
- Chosen: v2.3 through v2.6 milestones, then v3.0.0 for the complete distribution train.
- Advantage: preserves published v2.2 history and gives each large feature an independently testable release.
- Advantage: avoids presenting “Mobile 1.0” as a downgrade.
- Cost: more release operations and migration fixtures.
- Rejected: resetting Mobile to 1.0 because git history already exposes v2.2.
